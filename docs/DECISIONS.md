# DECISIONS

Нумерованные решения и отклонения от SPEC с числами. Все проверки — фактические запуски
на этой машине (RTX 3050 Laptop 4 GB, i5, Windows 11).

## D-001. Данные: процедурный миксер вместо Slakh2100
Slakh2100 (MIDI, ~104 ГБ) и MUSDB18-HQ не скачивались: на `E:` 369 ГБ, но загрузка и
разбор заняли бы больше времени, чем весь остальной проект. Обучение идёт на
процедурном синтезе (`ml/avis_ml/synth.py`, `mixer.py`) с метками кадр×полоса.

## D-002. Батч обучения 8
4096 MiB VRAM (RTX 3050 Laptop). `batch=8`, `T=64`, AMP; шаг ~0.6–1.2 с при
параллельной работе. Больший батч не проверялся (риск OOM).

## D-003. FE-v1: история `N0-HOP`, окна 2048/1024/512
Numpy-стриминг держит `N0-HOP` сэмплов, чтобы первый кадр заканчивался на HOP.
Torch-батч принимает `[B,n,2]`. Паритет numpy/torch и C# — ≤2e-3 (факт 3.9e-6).

## D-004. FE-v1: непрерывная треугольная нормировка
Веса полос — треугольные фильтры на общей лог-оси без «ступенек» между разрешениями.
Проверка: синус 1 кГц ≈ −6 дБ ±1; шум без ступенек >1.5 дБ.

## D-005. Windows App SDK 2.6.5
1.7 не собирается: отсутствуют MSBuild-задачи `AppxPackage`
(`Microsoft.Build.Packaging.Pri.Tasks.dll`, `Microsoft.Build.AppxPackage.dll`).
2.6.5 собирается чисто, unpackaged self-contained.

## D-006. D3D11: собственный P/Invoke вместо обёрток Vortice
`D3D11CreateDevice` и `D3DCompile` вызываются напрямую; Vortice используется для
интерфейсов. Причина: в используемой версии Vortice нет удобных
`Create{Vertex,Pixel}Shader(byte[])`. Шейдеры компилируются из HLSL на старте.

## D-007. Swapchain для SwapChainPanel
`CreateSwapChainForComposition` + `ISwapChainPanelNative` (IID
`63aad0b8-7c24-40ff-85a8-640d944cc325`, fallback `f92f19d2-...`).

## D-008. Скриншот: alpha = 255

прозрачным/белым. В `TakeScreenshot` alpha выставляется в 255.

## D-009. Исправление presence (найдено на smoke-модели)
`ObjectTracker` передавал `LastPresence` (изначально 0) в `ObjectParams.Build` как
`presenceOverride`, из-за чего presence всех объектов всегда был 0, а рендер пустым.
Теперь передаётся `-1` (вычисление из громкости); override `1` остался только для
барабанов в DSP. После фикса нейро-объекты рендерятся (проверено PNG).

## D-020. Фронтенд: SIMD по четырём сигналам

## D-021. Partial loudness: нормировка в дБ (найдено на визуальной проверке)
На PNG «Красивый» (YMode.Partial) все объекты прижимались к верхнему краю.
Причина: формула SPEC F `10·log10(partial^(1/0.23))` даёт sone-подобную величину
(+19 дБ медиана, +48 дБ p95 на процедурном миксе), а рендер ждёт дБ в шкале −70…0.
Добавлена нормировка на суммарную сжатию энергию кадра:
`partial = loud + 10/0.23·log10(Σ max(0, N'(E_k) − 0.3·N'(E_rest_k)) / Σ N'(PM_k))`.
Объект, владеющий всем спектром, получает `partial == loud`; замаскированный —
ниже. Это сохраняет смысл partial (вклад с учётом маскировки) и приводит шкалу к дБ.
Проверка: на миксе partial p50 −31 дБ (было +19), объекты распределены по вертикали,
PNG «Красивый» больше не обрезан сверху. Проверки сценариев partial не используют.

## D-023. Вылет UI на 0xC000027B: тема WinUI грузится через App.xaml, PRI обязателен в dist
Симптом: окно открывалось, но при нажатии «Настройки» (или `--settings`) процесс
умирал с `0xC000027B` в `Microsoft.UI.Xaml.dll`; управляемое исключение не
логировалось. В `%LOCALAPPDATA%\AVIS\crash.log` был только
`XamlParseException: Cannot find a Resource with the Name/Key
TabViewScrollButtonBackground`; `e.Handled = true` падение не отменяло.

Причины (обе подтверждены экспериментом):
1. В проекте не было App.xaml, и стили контролов (XamlControlsResources)
   добавлялись из кода. На Windows App SDK 2.6 такой вариант падает внутри
   framework: `COMException 0x8000FFFF` на `IApplication::get_Resources` или
   `Cannot find a resource with the given key: AcrylicBackgroundFillColorDefaultBrush`
   в конструкторе `XamlControlsResources`. Минимальный шаблонный проект с
   App.xaml работает; тот же проект без App.xaml (merge из C#) падает всегда.
2. `dotnet publish` не копировал `Avis.App.pri` в `dist\AVIS`. Без индекса PRI
   не резолвится `ms-appx:///Microsoft.UI.Xaml/Themes/...`, поэтому собранный
   dist падал на старте, хотя `bin` работал.

Исправление: добавлен `App.xaml` с `XamlControlsResources`, `App` стал
`partial` и вызывает `InitializeComponent()`; `Program.cs` остаётся точкой
входа (`DISABLE_XAML_GENERATED_MAIN`); сняты `AppxGeneratePriEnabled=false` и
`EnableDefaultWindowsAppSdkPRIResourceItems=false`; в csproj добавлен таргет
`PublishPriIndex`, копирующий PRI в папку публикации. В App оставлен
минимальный лог `%LOCALAPPDATA%\AVIS\crash.log` (пишется только на ошибках,
обрезается после 256 КБ) и обработчик `UnhandledException` с `Handled = true`.
Заодно починен титулбар: элемент для `SetTitleBar` не был в дереве (теперь это
строка 0 корневого Grid), поэтому кнопки CommandBar больше не наезжают на
Minimize/Maximize/Close.

Проверка (dist, Release x64): `--settings` 3/3 без падений; реальные клики мышью
по всем четырём кнопкам CommandBar, 8 заголовков групп, 2 TextBox (фокус + ввод),
3 выпадающих списка, 30–45 с работы — без `crash.log`; `--bench 3 --autoclose`
даёт FPS p50 180 и код 0; xUnit 7/7.

## D-024. Сброс настроек, чёрный фон окна и подсказки
Пользователь попросил три вещи: возврат к значениям по умолчанию, полностью
чёрный фон вместо серого (Mica) и подсказки при наведении.

**Сброс.** `AppSettings.ResetToDefaults()` копирует все свойства с атрибутом
`[Setting]` из свежего `new AppSettings()`. `BaseDirectory` и `ModelDirOverride`
атрибута не имеют, поэтому машинные пути (`--model`, расположение данных) после
сброса сохраняются. Кнопка «По умолчанию» стоит в заголовке панели настроек и
перестраивает панель целиком тем же путём, что и пресет, после чего вызывает
общий `OnSettingsChanged`.

**Чёрный фон.** Серый фон давал Mica-backdrop, просвечивающий через
premultiplied swap chain (альфа композита = яркость). Добавлено значение
`WindowMaterial.Black`: `SystemBackdrop` снимается, корневой Grid красится в
непрозрачный чёрный, swap chain остаётся premultiplied и композитится поверх
чёрного. Цвета сцены при этом совпадают с PNG-снимком (он и раньше
композитился над чёрным). Mica и Acrylic не изменились.

**Подсказки.** Короткие тексты у кнопок CommandBar и у списков источника/пресета;
у настроек — описание из `[Setting]` плюс строка «Диапазон … шаг … По
умолчанию: …» (для bool/enum/string — значение по умолчанию). Тултип ставится и
на Slider, и на его подпись; у TextBox его раньше не было вовсе.

Проверка (UIA + инжекция `mouse_event`, реальные наведение и клики, bin и dist):
подсказки видны у кнопок, списков, слайдеров, ToggleSwitch, ComboBox и TextBox;
сброс возвращает `SplatSize` 0,8 → 1 и пишет «настройки по умолчанию» в статус;
переключение «Материал» Black ↔ Mica меняет долю пикселей сцены < 8/255 с
94–95 % (avg RGB ≈1) до 0 %; `crash.log` пуст; `build.ps1 -Test` 7/7;
`publish.ps1` 298 МБ, `Avis.App.pri` на месте.

## D-035. P14: почему v2 не училась — EMA-лаг, NaN-градиент fp16 и голод головы pitch

Три независимых дефекта, найденных диагностикой (числа — фиксированный val,
120 процедурных + 120 реальных примеров, сид 777):

1. **EMA без разогрева.** `ema_decay 0.999` при 150–300 шагах почти не двигает
   веса: на шаге 150 EMA даёт pitch AP **0.104**, act IoU **0.0003** (модель
   «заморожена» около инициализации), а живые веса — AP **0.281**, IoU **0.966**.
   Валидация и выбор чекпоинта мерили не ту модель, отсюда ложные «деградации».
   Исправлено: `ema_update(..., step)` с разогревом `decay=min(d, (1+t)/(10+t))`
   (timm-style) — ранние шаги почти живые, к 8–12 тыс. шагов горизонт 0.999.
2. **NaN-градиент fp16.** Под AMP `sigmoid` в fp16 насыщается ровно в 1.0/0.0,
   и `binary_cross_entropy` на вероятностях даёт inf в backward → `g_act=nan`,
   шаги пропускались (прогон 1, шаг 380). Исправлено: модель отдаёт **float32
   логиты** (`act_logit/pitch_logit/sal_logit`) для лоссов, вероятности — только
   для метрик/ONNX; лоссы переведены на `binary_cross_entropy_with_logits`
   (focal и pos-weight — тоже в логитах). Добавлен guard: нефинитные градиенты
   → шаг пропускается, EMA не обновляется.
3. **Голод головы pitch.** При общем декодере `g_pitch` был ≈ в 500 раз меньше
   `g_emb`. Введены отдельные ветки-декодеры на голову (`dec_emb/act/pitch/sal`)
   после общего энкодера+GRU; параметров 2 987 535 при `hid 280` (цель 2–3 млн).
   ONNX-контракт шага не изменён.

## D-037. M-v3: исправления по итогам независимого ревью (стерео, SNR, prior, отбор)

Независимый аудит первой сборки M-v3 (до финального обучения) нашёл четыре
ошибки. Обучение остановлено на шаге 1220 и перезапущено с нуля после правок.

1. **Стерео-аугментация ломала образ L/R.** `_augment_stereo` считал mid/side и
   возвращал их как левый/правый каналы: при `L=R=1, width=1` правый канал
   обнулялся. Для Slakh (моно дублируется в L=R) это давало тишину в правом
   канале на всех реальных примерах. Исправлено: `left = mid + side`,
   `right = mid − side`, поворот применяется в пространстве L/R. Ширина и
   поворот остаются аугментациями: для моно-входа поворот даёт панораму
   (масштаб 0.76…1.24, энергия сохраняется), но не тишину.
2. **`_combine` перезаписывал уровни hard-cases.** Случайные усиления
   `loud − U(0,30)` дБ убивали задуманный SNR `pitch_noise` (−18…−3 дБ) и
   относительные уровни `close_pair`/`drum_bed`. Добавлен `relevel=False` для
   hard-cases: их уровни сохраняются, нормируется только финальный микс
   (−20…−8 dBFS, как раньше). Считается `hard_miss` — сколько hard-примеров
   билдер отклонил, чтобы фактическая доля была видна.
3. **Prior давал ложные пики на шуме.** Прежняя версия (`log1p` + нормировка на
   максимум кадра) давала 1.0 на любом кадре, включая шум (240 кадров шума:
   max 0.998), поэтому остаточный логит питча получал +1.5 на случайной полосе.
   Новая формула уровень-инвариантна: `ratio = (acc+1e-6)/mean(acc)+1e-6`,
   `prior = clamp((ln ratio − ln 3)/ln 12, 0, 1)`, счёт в fp32 даже под AMP.
   Измерено на FE-v1 (2 с, CPU): белый шум −10 dBFS — медиана максимума кадра
   **0.166**, p90 0.26, max 0.35; шум −40 dBFS — 0; синус 220 Гц −20 dBFS —
   **0.932** на 223 Гц; пила 330 Гц −24 dBFS — **0.911** на 331 Гц; тишина — 0.
   Ограничение: тон, полностью утопленный в шуме (S13: −24 дБ под −10 дБ),
   prior не выделяет — там работает только временное интегрирование GRU.
4. **Отбор чекпоинтов считался по hard-val.** `evaluate` суммировал все наборы,
   включая диагностический `hard` (48 примеров), поэтому composite был несравним
   с v1/v2.1. Теперь `evaluate` дополнительно считает
   `sel_pitch_ap/sel_act_iou/sel_l_dc/sel_n_examples` по proc+real, и
   `composite()` использует их; `pitch_ap`/`act_iou` по всем наборам остаются в
   `val.json` для диагностики.

Дополнительно:

- `export.py` предпочитает EMA-веса (`ck["ema"]`): `ckpt_last` хранит в `model`
  сырые веса, и дефолтная команда экспорта из AGENTS.md выгружала
  невалидированные веса. Добавлен `--golden-out` — golden-векторы версии можно
  писать в `artifacts/golden/<ver>/model`, не затирая `shared/golden/model` (v1);
  паритет PyTorch↔ONNX теперь сравнивает и `h_out`.
- `train.py`: `--resume` восстанавливает `best` из чекпоинта, а не пересчитывает
  его от текущих (возможно худших) весов.
- Повторный аудит (тот же субагент) нашёл две недоделки в правках и ещё две
  мелкие: (а) `_augment` (дисторшн `tanh(x·d)/tanh(d)`, усиление до +15 дБ)
  применялся **после** выставления SNR, поэтому реальный SNR в `pitch_noise`
  уезжал — теперь аугментация идёт первой, а масштаб шума считается от уже
  аугментированного тона; (б) паритет в `export.py` считался по знаковой разности
  `(a−b).max()` — заменено на `max|a−b|` для всех выходов; (в) при `--resume`,
  если стартовый composite выше сохранённого `best`, `ckpt_best` теперь
  перезаписывается, чтобы файл соответствовал `best`; (г) ONNX-сессия
  освобождается, если форма `h_in` не читается.
- Собственная проба после правок нашла **инвертированный знак SNR** в
  `_hard_pitch_noise`: `noise *= 10**(snr/20)` при `snr ∈ [−18, −3]` делал шум
  *тише* тона, т.е. фактический SNR был **+4…+18 дБ** вместо задуманного
  отрицательного. Теперь `10**(−snr/20)`; измерено на 10 отрисовках:
  −17.97, −7.79, −9.72, −17.78, −4.35, −5.64, −15.6, −10.0, −6.97, −5.78 дБ.
  Дополнительно `_tone_src` применяет задуманное усиление **после** `_augment`,
  поэтому `close_pair`/`drum_bed` держат относительные уровни: 1.6–4.4 дБ
  разброс в парах (задумано ≤6 дБ), drum_bed ≈12 дБ (kick/snare/hihat).
- Октавная неоднозначность prior зафиксирована как известное ограничение
  (REQUIREMENTS_V3): при отсутствующей основной (гармоники 2–6 от 220 Гц)
  максимум уходит на 2-ю гармонику ≈430 Гц; при наличии основной вершина на f0.
- SNR в `pitch_noise` оставлен **−18…−3 дБ** (в REQUIREMENTS_V3 было −18…−6):
  сложнее, порог не ослабляем; документ обновлён.

Проверка после правок: CPU-пробы prior/mixer (числа выше), preflight 300 шагов
(см. LOG), затем полный прогон 7000 шагов с нуля.

косинус полос падает ниже 0.60. v3.2 сдвинул метрику на +0.15, но порог не
перешёл. Значит один только миксер (пассивное добавление solo-примеров) задачу
не решает — нужен прямой терм в лоссе.

### v3.3: solo-coherence

`losses.solo_coherence(emb, active, solo)` = `mean(1 − cos)` активных полос к
среднему направлению примера, только на solo-примерах. Терм добавляется к
общему лоссу **вне** uncertainty weighting: иначе `log_var[0]` может выучить
даун-вейт всего DC-терма и заглушить новую цель. Отчётный `l_dc` остаётся
чистым, чтобы composite и выбор чекпоинта были сопоставимы с прошлыми прогонами.

`mixer_v3.batch` возвращает флаг `solo` (1.0, если в примере ровно один
источник), `validate.labels_of` его пробрасывает, лог печатает `coh`.
`configs/v3_3.yaml`: от `ml/models/v3_2/ckpt_ema900.pt`, 1200 шагов, lr 1e-4,
`solo_coh_w: 0.5`. Параметры модели, ONNX-контракт и пороги рантайма не менялись.

Почему нужен именно лосс, а не только данные: `deep_clustering` при `K < 2`
возвращает ноль (`if K < 2 ... return emb.sum() * 0.0`), т.е. **solo-пример
v3.2 вообще не давал градиента на эмбеддинг** — работали только головы
act/pitch/sal. Поэтому сдвиг косинуса 0.29→0.44 в v3.2 шёл через маску
активности, а не через геометрию эмбеддинга; сам эмбеддинг на solo-данных
не обучался. `solo_coherence` — первый терм, который напрямую стягивает все
полосы одиночного источника в одно направление.
